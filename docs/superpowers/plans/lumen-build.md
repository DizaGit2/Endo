## §0 How to use this plan

1. **One phase per session.** Open a fresh session, read §1 ledger → `NEXT PHASE TO RUN`. Confirm its `dependsOn` are `DONE`.
2. **Clear the phase's gaps first.** Each §3 phase lists **Preconditions (resolve before starting)** — open gap-register blockers, decisions (decision-sheet), and definitions it needs. If any is unresolved, do **not** start; resolve it (record in `ARCHITECTURE.md §A` + §4 here) or pick a phase whose gaps are clear. A session must never invent a clinical or legal value.
3. **Paste the phase's Kickoff prompt** (in its §3 entry) as the first message. Execute via `subagent-driven-development`: a subagent per task, strict TDD, one commit per task.
4. **Verify, don't narrate.** Run each task's commands; a phase is done only when its Exit criteria are proven with pasted output (`verification-before-completion`).
5. **Stop at NEEDS_REVIEW.** Fill the phase's `STATUS` block (pasted command output), set the ledger row to `NEEDS_REVIEW`, open the phase PR, stop. The human reviews (deep review for ⚠ phases), then flips the row to `DONE`.
6. **Anti-drift.** Docs change in the same branch as the code that invalidates them; this plan *references* `ARCHITECTURE.md §` rather than pasting; if you rename a type/path a later phase's tasks mention, fix that task text in the same `docs(plan)` commit; stamp the ledger SHA.

## §2 Architecture invariants  (the immutable spine — do not contradict without a human-approved `ARCHITECTURE.md §A` change)

- Request path: **HTTPS → Caddy → Keycloak JWT validation → controller → application → EF → Postgres**. Only Caddy is public.
- **Per-user envelope encryption:** every `*_enc` column is AES-256-GCM with a per-field IV, using a per-user DEK that is generated server-side, wrapped by the Vault Transit KEK, and stored in `user_keys.wrapped_dek`. The plaintext DEK is unwrapped via `IUserCryptoContext` (request-scoped) or `IJobCryptoContext` (job-scoped) and **never persisted, never logged, never cached beyond that scope**.
- **DEK is server-held, NOT password-derived** (background jobs decrypt while the user is offline). Lab PDFs are encrypted **server-side** (decision D5). The client never holds the DEK.
- **Erasure = crypto-shred:** deleting `user_keys` makes all the user's ciphertext permanently unreadable; object-storage objects under `{user_id}/` are also physically deleted **once the labs store exists (the `CryptoShredJob` MinIO branch is a tracked `TODO(P7a)` no-op until then)**.
- **.NET 10** (pinned via `global.json`). **Online-only client** (reads cache in Hive, writes never queue). Keycloak realm **`lumen`**.
- **Determinism:** `TimeProvider` everywhere (build-enforced: BannedApiAnalyzers RS0030 over backend/src); no live LLM in CI (record-replay); no `DateTime.UtcNow` in domain/app code.
- **Reference data** (`ref_hormone_range`, `ref_medication`, `ref_insight_rule`) is seeded via migration with `valid_from` + provenance, and is the single source of truth; the inference engine reads `ref_insight_rule` params, never hard-coded magic numbers.

#### Handoffs — the rules the generated client cannot carry

**`ARCHITECTURE.md §C.0` is the durable home** (new subsection, T22): Swashbuckle emits no `description`, so none of this phase's ~45 DTO XML docs reach `client/lib/api/`. §C.0 carries the write-semantics table (**full upsert** on `POST /cycle/events` — an omitted field CLEARS; **merge** on `POST /cycle/day/{date}` and `POST /checkin/quick` — an omitted field is left unchanged; **full replace** on `PUT /symptoms/{id}` and the three onboarding preference steps; **merge** on `PATCH /me` and `POST /onboarding/baseline`), plus `pauseReason`, `weightKg`, `diagnosedOn`, `T?`, the nullable+default trap and the six new `MeResponse` keys. **The deciding test for a write rule is how many surfaces write the row, not the HTTP verb.**

**P4b:**
- **Register the push device on EVERY app start** — not "first launch + token refresh". The cross-account detach is only self-healing because the victim's app takes its token back.
- **`diagnosedOn` is `String?`, not `Date?`** — hand-parse it as `yyyy-MM`. `format: date` would ship a runtime crash, because the generated `DateSerializer` calls `DateTime.parse`, which throws on `"2026-08"`.
- **Every generated property is `T?`** — no schema emits a `required` array, and T20 verified empirically that `[Required]`/`[BindRequired]` leaves the document byte-identical.
- **The P3b-era Hive `MeResponse` cache lacks SIX new keys** — `diagnosedOn`, `dob`, `endoStatus`, `heightCm`, `latestWeightKg`, `rasrmStage`. **The positive-control rule — the phase's most expensive lesson, learned across eight tests that passed but could not fail.** For every load-bearing assertion, ask: **"is what I am asserting also true *before* the code runs?"** If yes, it needs a **positive control in the same test** — establish the state first, then assert the code preserved or changed it. Two shapes account for all eight: *asserting an absence that is also the default state* (a sink asserted null in a container whose default is null — it passes with the writer deleted), and *asserting an invariant weaker than the behaviour under test* (`0..6` for a weekday offset, satisfied by every `% 7` implementation, right or wrong). **The structural check is primary; a mutation is only the backstop** — running a mutation catches the subset where some production line contradicts the assertion, but it cannot reach an assertion that is merely too weak, because no line is watched only by that assertion. Both times a mutation did catch one here, it came back **green**, and a reader could have flagged it without running anything. Where an assertion genuinely cannot be made falsifiable, say so, put a trip-wire on its premise, and point at where the real proof lives — do not fake a red run.

**What a mutation harness must prove (added at T9, after one produced false kills).** For every mutation it reports: **(1)** the mutated file's on-disk bytes must actually differ from the pre-mutation baseline before the test run is trusted as a result — never inferred from the runner's exit status or summary text — and a failed application (anchor not found, patch rejected, no diff) must be reported as a distinct **`NOT APPLIED`** state that is never countable as a pass or a kill; **(2)** any "which tests reddened" list must be sourced from each test's own individual result line, never from a summary or trailer a runner is free to truncate. T9's harness appended its anchor-not-found placeholder to the same list it used for reddened test names, so **a mutation that never touched the tree presented as one that killed a test** — `dart format` had moved the lines its anchors pointed at. Two of that round's mutations reported "1 red" having never been applied; re-running under the corrected harness surfaced **five more** drifted anchors that would have read as kills.

**(3) A kill is positively identified, never inferred from redness (added at T10, after a *second* harness manufactured one — and after rule (1)+(2) failed to prevent it).** T10's harness satisfied both clauses above — the bytes did differ, the reds *were* read from individual result lines — and still printed KILLED for a mutation that did not compile, because `loading <path> [E]` matches the red-line shape. Blacklisting that string closes today's instance, not the class. Both harnesses failed the same way one level up: **they inferred a kill from redness *anywhere* instead of positively identifying the aimed test's own failure.**

So: before mutating, record the aimed test's own per-test result line as GREEN together with the run's executed-test count. Count `KILLED` only when the mutated run executes that **same count**, the **aimed** test's own line is the red one, and its failure message names *the expectation that failed* rather than an error raised before the assertion ran — and paste that line verbatim into the report. Any red matching no test in the recorded inventory — a compile failure, an anchor-not-found placeholder, a crashed or timed-out runner — is an **`INVALID_RUN`**: neither a kill nor a survival, forcing a re-run once the harness is fixed.

**(4) Three mechanical obligations added at T8b, each after the rule failed for a *new* reason.**
- **A widget test's kill cannot be judged from the JSON `error` event.** `flutter_test` catches a `testWidgets` failure, prints it, and re-registers it as a plain **string** (`flutter_test/lib/src/test_exception_reporter.dart:28-43`), so `isFailure` — defined as `error is TestFailure` — is **false for every `testWidgets` test** and the `error` text names no expectation. Satisfy the "message names the failed expectation" obligation from the **aimed test's own `print` events**, requiring both `The following TestFailure was thrown running a test:` and an `Expected:`/`Actual:` block — that pairing is what separates a failed expectation from a tap that missed, a finder that matched nothing, or a `pumpAndSettle` timeout. Plain `test()` cases keep `isFailure: true` and need no special handling. **The two routes are mutually exclusive and selected by the test's type**: a harness must dispatch on whether the aimed case is `testWidgets` or `test()`, and demanding the `testWidgets` evidence pair from a plain `test()` is a **harness defect that presents as `INVALID_RUN`** — T12 lost a round to exactly that, and the wording above invited it. Note also that `isFailure: true` alone can identify a failure that **names no expectation** in an `Expected:`/`Actual:` form — mocktail's `No matching calls (actually, no calls at all)` is the common one — so when a claim rests on such a mutation, **re-aim the identical mutation at a `testWidgets` case as well**, which is what buys a printed expectation.
- **"The same executed count" means the number of `testDone` events with `hidden: false`** in the JSON run — never `flutter test`'s trailing `+N`, which is a different report of the same engine and must be quoted separately as measured. If the two disagree, **the harness is at fault, not the reporters**: key the inventory on the JSON **`test.id`**, never on the test's name. Names repeat across this suite — `renders no dingbat glyphs` alone occurs 16 times — and a name-keyed harness silently collapses them, making a kill unattributable whenever the aimed name is not unique. Aim every mutation at a name that is unique, and refuse an ambiguous aim rather than guessing.
- **Make the machine quiescent before a round, and prove it.** `Get-Process dart, flutter, flutter_tester` must return nothing — **`TaskStop` on a background shell does not kill its `dart` grandchild on Windows** — and every anchor must be present on disk unmutated with every mutated form absent. Re-verify both afterwards, plus each revert's byte fingerprint against its per-mutation baseline. Treat any prediction miss, unexpected `NOT APPLIED`, or baseline fingerprint differing from the quiescent file as evidence about the **environment first**: discard the whole round and re-run. T8b lost two rounds this way, and the tell was arithmetic — a 15-byte mutation's fingerprint appearing as another mutation's *baseline*.

**(5) Two more obligations, added at T5d.**
- **A shared matcher must report through `expect(actual, matcher, reason: …)`, never `fail(…)`.** A bare `fail` throws a `TestFailure` with no `Expected:`/`Actual:` block — that block is written only by matcher's failure formatter — so a mutation aimed at a `fail()`-based matcher returns `INVALID_RUN` and **the matcher cannot be mutation-certified by this phase's own rule**. T5d hit exactly this and had to convert `expectNoDingbats` mid-round.
- **When a round adds pinning tests to a shared matcher, re-run every earlier mutation aimed at that matcher.** New tests change what those mutations kill. T5d re-ran only four of its mutations at HEAD, and the three it skipped were precisely the ones that would have contradicted a claim it shipped — a reviewer later applied one of them and reddened a test the report had called unkillable.

**(6) Measure a mechanism claim before writing it down — including one handed to you by a reviewer or by this plan.** T5d had **three** plausible mechanism claims fail measurement in one task: "the own/merged split appears where the row is a live control" (its own fixture disproved it), "an explicit container is an `isCompatibleWith` case" (it is `isSemanticBoundary`, a separate mechanism), and "a `suffixText` merges into a field's accessible name" — the last **relayed to it by a reviewer through me**, and false: `_AffixText` gives the suffix its own node, so only the hint ever appended, and the test comment asserting otherwise had been wrong since before the task began. A mechanism claim in shared infrastructure is load-bearing for every task that reads it, and this phase's evidence is that plausibility is not predictive. Probe it, paste the probe, and treat an inherited claim exactly like your own.

**(7) A fix round must mutate the code the fix ADDED, not only revert the defects it repaired (added at T13).** Reverting each review-found defect is a valid regression gate — it proves those specific defects are now caught — but it is strictly narrower than round 1's standard, because the fix's *own* new logic then ships with no evidence its tests can fail. T13's round 2 reverted two defects and never mutated `PushToken.sendable`'s internals (`||`→`&&`, checking one half only, the empty-string vs whitespace-only boundary) or the merge-fallback construction that replaced the reverted seed. Budget a round's mutations across both: the reverts **and** at least one aimed at the new code's discriminating branch. Where the new code is a guard, the mutation that matters is the one that widens it, not the one that deletes it.

**(8) Certifying a mutation that makes a Future REJECT — measured at T14, and neither obvious route works.** A rejected Future **cannot** be certified with `completes`/`completion`: matcher 0.12.19 attaches only a success `.then()` on both paths (`future_matchers.dart:53`, `async_matcher.dart:52`), so nothing ever constructs a `TestFailure` and **`isFailure` stays `false`** — the JSON reporter's field is literally `'isFailure': error is TestFailure` (`test_core-0.6.17/lib/src/runner/reporter/json.dart:294`). And `fail()` is out-of-contract for the mirror-image reason: it gets `isFailure: true` but produces **no `Expected:`/`Actual:` block**, because that block is written solely by matcher's failure formatter — the same defect obligation (5) already names. **The route that satisfies both: capture the rejection, then assert on the captured value with a real matcher.**

```dart
Object? err;
await f.then<void>((_) {}, onError: (Object e) => err = e);
expect(err, isNull, reason: '…');                       // Expected: null / Actual: <NotFoundFailure>

await expectLater(f.then<Object?>((v) => v, onError: (Object e) => e),
                  completion(expected), reason: '…');   // Which: emitted <NetworkFailure>
```

Correct the natural misreading before it spreads: **this does not make `completes` useless.** It still fails a non-Future, and `completion(m)` still fails a wrong *value* — verified by mutating a stub's return and watching `Which: emitted Date:<2026-05-02>`. The gap is narrow and specific: neither can convert a **rejection** into a `TestFailure`.

**When two candidates both fail, that is not evidence that none works — it usually means the search stopped early.** T14 produced this shape **three times in one task**: the provider shape (three candidates measured and rejected, while `keepAlive()` *before* the await with `link.close()` on failure — Riverpod's own cache-on-success-only idiom — was never tried); the rejection-certification route above (`completes` and `fail()` tried, capture-then-assert not); and my own fix list, which relayed the first wrong route as an instruction. Each time the measurement was sound and the conclusion was "therefore the better of these two". Before concluding a constraint is unsatisfiable, name the *shape* of what would satisfy it and ask whether the language or framework already has an idiom for that shape.

**Auditing a large test diff cheaply (from T14's ~370-line churn):** extract every `expect*`/`verify*` statement from both revisions, whitespace-normalise, sort, and diff the **sets**. That distinguishes formatter reflow from a dropped assertion in one pass — T14's churn came back 62 → 65 with zero `skip:`, and the two apparent removals were the same statements re-wrapped by `dart format`. Reading a reflowed diff line-by-line cannot tell you that.

**A negative semantics assertion needs a handle that OWNS a semantics node (found at T15, and it binds every screen still to come).** `tester.getSemantics` walks **up** the render tree, so asserting "this is not a button" on a widget that contributes no semantics of its own silently tests an *ancestor*. Verified to bite under three different mutation shapes, including a third button added *outside* the scoped subtree.

**What a blocked-text golden cannot evidence — two false self-descriptions have now been found in `golden_app.dart` itself.** T13 found that the images are only insensitive to copy **at equal rendered width** — T13 originally recorded this as *equal character count*, and **T16 measured that wrong**: two equal-length label swaps reddened both goldens by 847 px, because blocked text is laid out with real proportional glyph metrics **before** being blocked, so the rect follows the rendered width and equal character count does not imply equal width in a proportional font (`obscureText` preserves run length, so a length-changing copy edit moves pixels). **(9) A semantics-guard mutation must inject a widget with real geometry — a zero-size one is INERT, and its survival is a harness artifact, not a coverage gap (found at T17, verified twice).** Flutter **drops zero-geometry nodes from the compiled semantics tree entirely**: `isInvisible => !isMergedIntoParent && (rect.isEmpty || (transform?.isZero() ?? false))` (`semantics.dart:2907`), `shouldDrop(node) => node.isInvisible` (`object.dart:5746`), `children.removeWhere(shouldDrop)` (`object.dart:6246`). Measured on one widget changing only geometry: `Semantics(button: true, child: SizedBox())` → **31/31 pass, nothing reddens**; the same with `SizedBox(width: 24, height: 24)` → exactly one red naming the node. So `SizedBox()`, `SizedBox.shrink()`, `Offstage`, `Visibility(visible: false)`, `Transform.scale(scale: 0)` and zero-opacity subtrees all produce mutations that **cannot** kill. The escape clause is `isMergedIntoParent`. **Before concluding a guard failed to bite, prove the mutation was LIVE** — assert the injected node is findable at all, or run it against a control that should see it. Reporting an inert mutation as "the guard has a hole" is a false `INVALID_RUN` of exactly the shape this phase has already produced three times.

**(10) A compile-time property has a compile-time probe — "not runtime-demonstrable" is not the same as "not demonstrable" (added at T17).** T17 declined to manufacture a synthetic runtime test for an exhaustive `switch` over a `sealed` union, which was right; but it also called the property undemonstrable, and the reviewer disproved that in about thirty seconds by adding a **throwaway fourth variant** and running `flutter analyze`: `error - The type 'CacheResult<DashboardView>' isn't exhaustively matched … non_exhaustive_switch_expression`, while the file still using the old `is`/`as` shape produced **no error at all** — which is precisely the contrast the fix buys. Probe reverted, source hash restored. When a claim rests on a type-level or analyzer-level guarantee, **probe it with the analyzer**: add the variant, remove the annotation, widen the type, and read the diagnostic. Do not let "compile-time, therefore unprovable" harden into a habit.

**(11) A test must not source its expected value from the production symbol it is checking (found at T18).** `expectRetryReissuesOneRequest(label: kQuickCheckinRetryLabel)` resolved the label as `find.text(label)` with **no membership check**, so the assertion held under *every* mutation of that constant — changing it to `'Save again'` left all 44 tests green **and the P4b exit criterion unmet**. Every other write screen in the repo passes a literal. **Assert against a literal, or against a closed set the production value must belong to** (`expect(kRetryLabels, contains(kQuickCheckinRetryLabel))`). This is the general form of the vacuous assertion: the expectation is *correct*, and it is evaluated somewhere it cannot fail.

**T18 produced three instances of that same shape in one task, and they are worth keeping together because none was a wrong expectation:** (a) the self-certifying label above; (b) a guard whose tests never varied the guarded input independently — every payload test supplied value-null and touched-false *together*, so nothing distinguished "sends what the caller says was touched" from "sends whatever is non-null", and deleting either guard left the suite green; (c) an assertion **sampled at a moment when both outcomes look identical** — a single bare `pump()` after a scrim tap cannot separate "dismiss blocked" from "dismissing, mid-animation", so the aimed mutation left it green until a bounded pump sequence replaced it. **Before trusting a green test, ask what it would take for it to be red**, and prefer a mutation to an argument.

**What a blocked-text golden CANNOT evidence, consolidated (four measured corrections to one shared helper).** Not text opacity (T15). Not copy at equal **rendered width** — not character count; `flutter_test`'s default font is fixed-advance but alchemist's `loadFonts()` swaps in proportional fonts inside a golden (T13, corrected at T16, mechanism corrected again at T16's re-review). **(12) Verify mutation reverts with `git hash-object`, not `sha256sum` — and never revert with `git checkout --` (found at T19).** This repo has **`core.autocrlf=true` while the committed blobs are LF**, so `git checkout -- <file>` **rewrites the worktree file as CRLF and silently changes its fingerprint**. A revert then looks failed when it succeeded, or a baseline looks unfamiliar when it is correct. Revert by byte-exact copy from a pre-mutation snapshot and compare with `git hash-object` (CRLF-safe). **This is a live third candidate explanation for T14's unexplained fingerprint mismatch**, which was left open between "mutated before formatting" and "mis-transcribed" — and unlike either, this one is measured and reproducible.

**(13) Two failure shapes beyond the vacuous assertion, both found at T19.**
- **A fix that CANNOT RUN.** T19 added `.toUtc()` to normalise a timestamp before deriving cache keys. built_value's `Iso8601DateTimeSerializer` **throws `ArgumentError` on a non-UTC `DateTime`**, so anything that can reach the wire is *already* UTC and the call is a no-op — while a local one crashes inside `write()` with an error `cachedWrite` catches neither of, so the keys are never used. **The doc's stated benefit described a path that cannot execute.** Not a wrong mechanism and not a vacuous test: a correct-looking change on a dead branch. Ask what input reaches this line, and whether such an input can exist.
- **A FIXTURE that cannot distinguish the production input from a wrong one.** Production supplies `fallbackDay` as `Date.toDateTime()` — **local** midnight carrying the server's civil fields — while every test passes `DateTime.utc(...)`. Both read the same civil fields, so nothing distinguishes them, and a future "consistency" edit adding `.toUtc()` there would be **a no-op in every test and a real off-by-one-day bug in production**. When a test constructs its input differently from the caller, ask whether the difference is observable.

**Solve the problem the operation actually has (T19).** The timezone question looked like *"which day is correct?"* and had no offline answer — the client has the timezone **name** but no tz database. But these keys are used **only** for ambiguous-failure invalidation, where **under-invalidating costs duplicate clinical rows and over-invalidating costs a cache miss**. That asymmetry is one-directional, so a **`{D−1, D, D+1}` window** is provably exhaustive (IANA offsets span −12:00…+14:00) and needs no round trip. **The operation never required a correct answer, only a superset** — but apply it to the *explicit* branch only, since the `fallbackDay` branch is already server-exact and widening it would trade a right answer for three wrong-adjacent ones.

**Predict which tests should redden, and check that exactly those did.** A mutation whose *pattern* of reds matches the prediction is far stronger evidence than one that merely produces reds — T10's strongest proof was that deleting a flag reddened the empty-state assertions and the shell goldens while leaving the prefilled assertions and baseline goldens green, which is what identified the discriminating assertion and simultaneously showed an earlier mutation had never vouched for it.

**Four further ways a harness can report a kill that is not one:** a **dirty baseline** (the aimed test was already red — so the green baseline must be recorded *per mutation*, in the same invocation shape, not once per round); an **unreverted predecessor** (needs a hash check that the tree matches the baseline *after* each revert, not merely that the mutation applied); **collateral redness** (the mutation throws during build so the whole file reddens and the aimed assertion never evaluates — this is why the failure *message* must be inspected, not just the test name); and **order- or environment-dependent redness** (a kill that does not reproduce on a second mutated run is not a kill). **And the honest limit: a vacuous assertion can genuinely redden**, so no harness change catches that shape — only the positive-control rule does. **And read a mutation's result per-assertion, not per-run:** T7 found that the mutation which exposed its vacuous test was *byte-identical* to one run two rounds earlier, which had reddened **seven other tests** — so the run looked caught, and the one test that sat it out hid inside the red. A red run is not evidence that any *particular* assertion discriminates.

**Controller shape rule — binds the twelve validate-then-reject controllers still to come (T9–T22b).** An `AsyncNotifier`'s synchronous `state =` write races its own `build()` future: Riverpod assigns the build result unconditionally when it lands, so a rejection written first is silently dropped and the button looks dead. Before touching such a controller, classify its `build()`:
- **Empty build** (no `await`; the initial state is a fixed value): convert to `Notifier<AsyncValue<T>>` with a synchronous `AsyncValue<T> build() => const AsyncData(<initial>);`. This deletes the race at the root — there is no build future left to lose to. Behaviour-preserving where `build()` was already empty.
- **Loading build** (a real `await` — a repository fetch or cache read, as in `ProfileController`): **do not convert.** The `AsyncNotifier` is earning its keep, and hand-rolling the load trades this race for a worse bespoke one. Write every rejection through `AsyncValue.guard(...)` rather than a bare synchronous `state = AsyncError(...)`, or gate the mutating action on a settled controller.
- **`await future` is not the guard.** It resolves with the first non-loading state, so on a second submit after a rejection it rethrows the *previous* failure.
- **Test rule, in every one of the twelve tasks' acceptance criteria:** a controller test that reads a notifier and immediately calls a mutating method must settle the container first (`await container.read(xProvider.future)` or an equivalent pump). Reading-then-mutating without settling asserts on an undefined race between two writers, not on the code — whichever shape the controller has.

**Find controls by a stable handle, not by what they announce (added at T5c).** Screen tests locate a control with `find.byKey`/`find.byType` and use `find.bySemanticsLabel` **only inside assertions about what is announced**. The coupling bought no coverage: the one test that actually states the rule caught the change on its own. Do not retrofit the two green screen files; apply it from T11 onward.

**Never run `dart format` above a named file list (found at T13).** The repo is not format-clean — **126 of 304 files** still differ (`lib/api` **55**, `lib/core` 16, `lib/features` 6, `lib/shared` 3, tests 46) — and **nothing in CI gates formatting**.
