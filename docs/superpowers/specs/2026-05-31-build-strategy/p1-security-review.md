# Lumen P1 Spine — Deep Adversarial Security Review

## 1. VERDICT

The safety-critical machinery is **fundamentally sound at its cryptographic and tenant-isolation core, but NOT merge-ready** because the request-handling perimeter around it is unfinished. The good news is real and verified: `AesGcmFieldCipher` uses a fresh 96-bit CSPRNG nonce, 128-bit tag, and validated 256-bit key per call (`nonce ‖ ct ‖ tag`, no nonce reuse); the DEK is CSPRNG-generated and zeroed in `finally` blocks in `DekProvisioner`, `UserCryptoContext.DisposeAsync`, and the `/onboarding/start` profile path; `UserCryptoContext` request-scopes the DEK behind a single-flight gate; and tenant isolation is correct — `GET/PATCH /me` and the DEK lookup all key off `current.UserId` derived solely from the validated token `sub` (`CurrentUserAccessor`), never from client input, with `MapInboundClaims=false` + `NameClaimType="sub"`. JWT signature, issuer, and lifetime validation are intact via OIDC JWKS. However, three classes of defect block merge: (a) **`/onboarding/start` is a non-atomic, anonymous, unvalidated multi-system write with no exception handler** — any failure after the Keycloak `CreateUserAsync` orphans an IdP identity and permanently bricks that email for sign-up (409→500 on retry), and the raw 500 leaks exception detail (developer page in dev/CI because the container never pins `ASPNETCORE_ENVIRONMENT`); (b) **the rate limiter is defeated** — it partitions on `RemoteIpAddress` with no `UseForwardedHeaders`, so behind Caddy every anonymous caller collapses into one global 60/min bucket trivially exhausted to DoS all sign-ups; (c) **PII leaks on error paths** — the redaction enricher ignores `logEvent.Exception` and only redacts `/users/{guid}`-shaped paths, so bare `sub` GUIDs and emails in exception messages reach logs. The DEK is also un-zeroably copied into managed base64 strings, and neither envelope layer binds per-user associated data. None of these is a live break of same-user confidentiality today, but several violate the documented §F invariants and the GDPR crypto-shred / no-PII-in-logs guarantees enough to gate the merge.

## 2. MUST-FIX BEFORE P1 MERGE

### M1. `/onboarding/start` non-atomic multi-system write → orphaned identities + permanent sign-up brick
**Files:** `backend/src/Lumen.Api/Program.cs:118-179`, `backend/src/Lumen.Infrastructure/Auth/KeycloakAdminClient.cs:36-44`
**Issue:** Order is Keycloak `CreateUserAsync` (Program.cs:131) → DB `SaveChangesAsync` (153) → `ProvisionAsync` DEK (155) → profile write (170), with no transaction and no compensation. Any failure after line 131 (DB down, unique `EmailHash` violation — index confirmed at `LumenDbContext.cs:20` — Vault unreachable, cancellation) leaves an orphaned Keycloak user. On retry, Keycloak returns 409, which `KeycloakAdminClient.cs:37` maps to `InvalidOperationException("A user with that email already exists.")` → unhandled 500. The email is now permanently un-onboardable: the user can authenticate but has no DB/DEK rows, so `GET /me` returns 404 (Program.cs:189) and any crypto path throws `"No DEK provisioned for user {userId}"` (`UserCryptoContext.cs:33`). An attacker can also pre-register victim emails to lock them out. A crash between line 153 and 155 leaves a `User` row with no `user_keys` → 500 on first crypto touch.
**Fix:** Wrap the DB writes in one EF transaction (`await using var tx = await db.Database.BeginTransactionAsync(ct)`); provision the DEK inside the same unit of work as the `User` row. On any exception after the Keycloak create, run a compensating delete of the just-created Keycloak user, OR create the Keycloak user only after DB rows are durably staged. Treat a 409 where the Lumen row is absent as **resume onboarding**, not a hard error.

### M2. No global exception handler → raw 500s, stack-trace leakage, error oracle
**File:** `backend/src/Lumen.Api/Program.cs` (no `UseExceptionHandler`/`AddProblemDetails`/`UseStatusCodePages` anywhere — grep-confirmed)
**Issue:** Unhandled exceptions from `CreateUserAsync` (`EnsureSuccessStatusCode`, the 409 `InvalidOperationException`, `Guid.Parse` on a malformed Location header), `SaveChangesAsync` (`DbUpdateException` on the unique `EmailHash` index), Vault calls, and crypto bubble to the framework default. `deploy/docker-compose.yml:25-30` sets `ASPNETCORE_URLS` but never `ASPNETCORE_ENVIRONMENT`, so dev/CI returns the developer exception page (stack traces, connection strings, internal types). Even in Production this is an error oracle distinguishing duplicate-email from other failures, and the 409 maps to 500 instead of 409.
**Fix:** Register `builder.Services.AddProblemDetails()` and `app.UseExceptionHandler()` mapping known exceptions to clean codes (409 duplicate, 400 validation, 502 upstream Keycloak/Vault) with a generic body + correlation id for the rest — never the message/stack. Pin `ASPNETCORE_ENVIRONMENT=Production` for the container.

### M3. Rate limiter defeated behind Caddy → global sign-up DoS
**File:** `backend/src/Lumen.Api/Program.cs:72-83` (and no `UseForwardedHeaders` — grep-confirmed)
**Issue:** Partition key is `User.FindFirst("sub") ?? Connection.RemoteIpAddress ?? "anonymous"`. `/onboarding/start` is anonymous, and `deploy/Caddyfile.local:8` proxies all traffic via `reverse_proxy api:8080`, so `RemoteIpAddress` is always Caddy's container IP. Every anonymous caller shares ONE fixed-window 60/min bucket with `QueueLimit=0`. A single attacker sending 60 requests/min denies sign-up to all legitimate users (global DoS) while still creating up to 60 Keycloak users + Vault DEKs/min (cost amplification). 60/min is far too high for an account-creation endpoint that fans out to Keycloak + bcrypt + Vault.
**Fix:** Register `app.UseForwardedHeaders(new ForwardedHeadersOptions { ForwardedHeaders = ForwardedHeaders.XForwardedFor })` with `KnownProxies`/`KnownNetworks` restricted to the Caddy container/subnet (do NOT trust arbitrary `X-Forwarded-For` — that would re-introduce IP spoofing), placed **before** `UseRateLimiter`. Add a dedicated tighter limiter for `/onboarding/start` (a few sign-ups/min per real IP plus a global cap), and update the Caddyfile to forward the client IP.

### M4. PII (emails, bare `sub` GUIDs) leaks into logs on error paths
**File:** `backend/src/Lumen.Infrastructure/Logging/PiiRedactionEnricher.cs:21-34`
**Issue:** The enricher only rewrites scalar **string** properties and only redacts (a) email-shaped substrings and (b) GUIDs in a literal `/users/{guid}` path (regex line 18). It never inspects `logEvent.Exception`, where `UseSerilogRequestLogging` and unhandled errors attach the exception. Bare `sub` GUIDs — e.g. `UserCryptoContext.cs:33` `"No DEK provisioned for user {userId}"` and `DekProvisioner` paths — are not in a `/users/` path and are not redacted. The `sub` is the stable cross-system user key; correlating log lines to it in a special-category-data app is a §F / GDPR violation. Combined with M2 (no exception handler), `DbUpdateException` on the unique `EmailHash` index and similar errors log verbatim.
**Fix:** Scrub `logEvent.Exception?.ToString()` when present; generalize the GUID regex to any standalone GUID token (or hash to a short non-reversible id per §F's `/users/{sha256-short}`); walk structured/destructured properties recursively; prefer logging a correlation id over raw messages. Pair with M2 so error paths emit a sanitized event.

### M5. No server-side password policy on `/onboarding/start`
**Files:** `backend/src/Lumen.Api/Program.cs:128`, `deploy/keycloak/realm-lumen.json` (no `passwordPolicy`, no `bruteForceProtected` — confirmed)
**Issue:** Validation is only `IsNullOrWhiteSpace(request.Password)`; the password is forwarded verbatim to Keycloak, and the realm has no `passwordPolicy`, so a single-character password is accepted for a health/special-category account. With `directAccessGrantsEnabled:true` on the `api` client (realm-lumen.json:25) and no brute-force lockout, weak credentials are trivially brute-forced → direct GDPR Art. 9 exposure. No upper bound feeds the oversize-input DoS below.
**Fix:** Enforce server-side policy before calling Keycloak (min length ~12, max ~128, complexity/breach check) returning 400, **and** set a realm `passwordPolicy` plus `bruteForceProtected:true` with lockout as defense in depth.

> Note on **JWT audience (`ValidateAudience=false`, Program.cs:60)**: marked KNOWN-DEFERRED below, but the combination with `directAccessGrantsEnabled:true` on `api` and a second public `mobile` client in the same realm makes token-confusion real. I recommend landing the **interim `azp`/`typ` claim check before merge** even though the full audience mapper is P11 — it's cheap and closes the token-confusion hole without the mapper.

## 3. FIX-SOON (medium — P1 or early P2)

- **Unauthenticated email-enumeration oracle.** `backend/src/Lumen.Infrastructure/Auth/KeycloakAdminClient.cs:37` surfaces 409 as a distinguishable error; with `loginWithEmailAllowed:true` and `username=email`, an anonymous attacker confirms who has a Lumen account — itself a special-category health inference (GDPR Art. 9). Fix: uniform onboarding response regardless of existence; handle duplicates server-side; add CAPTCHA/email-verification + the per-IP limit from M3. (Largely resolved once M1+M2+M3 land.)
- **No per-user binding (AAD / Vault Transit `context`).** `VaultTransitKeyWrapper.WrapAsync/UnwrapAsync` (lines 26-39) pass no `context`; `AesGcmFieldCipher` passes no `associatedData`. Nothing cryptographically ties a `wrapped_dek` or `*_enc` blob to its `UserId`, so a DB-write attacker can transplant rows between users and a backed-up `wrapped_dek` replayed after a crypto-shred delete still unwraps — weakening both tenant isolation and the erasure guarantee at the storage layer. Fix: pass `UserId` as Vault Transit `context` (derived key) and as AES-GCM `associatedData` (plumb `UserId` into `UserCryptoContext` cipher calls). Defense-in-depth, not a live break, but the model claims isolation it doesn't enforce.
- **Plaintext DEK lingers in un-zeroable managed strings.** `VaultTransitKeyWrapper.cs:28` `Convert.ToBase64String(dek)` and `:38` `result.Data.Base64EncodedPlainText` materialize the plaintext DEK as immutable GC-heap strings that `ZeroMemory` cannot reach — partially defeating the "zeroed after use" invariant; recoverable from any process/crash/swap dump. Fix: minimize/pin exposure (`Convert.TryToBase64Chars` into a clearable rented buffer), document the residual VaultSharp string as accepted risk, ensure prod core dumps are disabled/encrypted, and rely on KEK rotation.
- **Input size/format validation missing.** `OnboardingStartRequest` fields (Program.cs:240) are unbounded; no `HasMaxLength` in `LumenDbContext` (grep-confirmed); no email-format check; no `MaxRequestBodySize` override. Anonymous callers can POST multi-MB `DisplayName` (encrypted+stored) / `Locale` / `Timezone` / `PolicyVersion` → CPU/DB amplification, and garbage emails feed the orphan/500 path. Fix: per-field max lengths + `MailAddress` format check + BCP-47/IANA validation (`TimeZoneInfo.TryFindSystemTimeZoneById`), matching `HasMaxLength` in `OnModelCreating`, tight Kestrel body limit.
- **Fragile Keycloak response parsing.** `KeycloakAdminClient.cs:43-44` uses `Guid.Parse` on the last Location segment and throws raw exceptions; a malformed/edge-case Location (KC version diffs, trailing slash) throws **after** the user is created → orphan + 500. Fix: `Guid.TryParse` with a typed sanitized domain exception; translate non-2xx into typed `DuplicateUser`/`UpstreamUnavailable`/`InvalidUserInput` carrying no raw upstream body, mapped to 409/502/400.
- **Over-scoped Keycloak service account.** `deploy/keycloak/realm-lumen.json:46-48` grants `["manage-users","view-users","query-users"]` though P1 only does `CreateUserAsync`. `manage-users` also permits resetting/deleting any user's credentials — so a leak of `dev-api-secret` is full multi-tenant account takeover. Fix: drop the redundant `view-users`/`query-users`; prefer a fine-grained policy or a create-user-only client; add audit on user.create/credential-reset; treat the secret as high-value and rotate.
- **Realm hardening gaps.** `realm-lumen.json`: no `bruteForceProtected`, no `passwordPolicy` (overlaps M5), no refresh-token rotation (`revokeRefreshToken`/`refreshTokenMaxReuse` unset) with 30-day `ssoSessionIdleTimeout`/`MaxLifespan`, and `directAccessGrantsEnabled:true` on the confidential `api` client which only uses `client_credentials`. Fix: enable brute-force lockout, set `directAccessGrantsEnabled:false` on `api`, enable refresh-token rotation, shorten idle timeout.
- **Health readiness probes the wrong config.** `Program.cs:100-113` `/health/ready` reads `VAULT_HOST`/`VAULT_PORT`, but the real crypto path reads `Vault:Address` (`VaultOptions`) — readiness doesn't reflect the dependency the API actually uses (ties into S-config below). Fix: align readiness with the configured Vault/Keycloak addresses.

## 5. NICE-TO-HAVE (low)

- **`DekProvisioner` check-then-insert isn't true single-flight** (`DekProvisioner.cs:21-36`). Two concurrent `ProvisionAsync` for the same user both see `exists==false`; the loser's `SaveChanges` throws a PK violation → 500 + wasted Vault op. Not a key-compromise (PK prevents two persisted DEKs, loser's DEK is zeroed). Fix: catch `DbUpdateException` as idempotent no-op, or `INSERT ... ON CONFLICT DO NOTHING`. (Mostly subsumed once M1's transaction lands.)
- **Unsynchronized fast-path read of `_dek`** (`UserCryptoContext.cs:26`). Double-checked locking without a volatile/`Interlocked` publish; worst realistic case is one redundant unwrap (context is request-scoped). Fix: `Volatile.Read/Write` or mark `_dek` volatile. Cheap hardening.
- **No DB-level FK / cascade between `users`, `user_keys`, `user_profile_enc`, `consent_records`** (`LumenDbContext.cs:13-46` declares no relationships; `init.sql` creates no tables). The crypto-shred precondition relies on deleting `user_keys`, but nothing DB-enforces the linkage or prevents orphaned `user_profile_enc` rows. Worth adding explicit FKs (and a documented erasure that deletes the key row) so the erasure guarantee is schema-backed, not just convention.
- **`emailVerified=true` set on unverified addresses** (`KeycloakAdminClient.cs:27`) and **`email_hash` is unsalted SHA-256** (`Program.cs:133-134`) outside the crypto-shred boundary — enables offline membership confirmation surviving erasure/backups. Consider HMAC with a Vault pepper and a real email-verification step (overlaps the enumeration-oracle fix).
- **Pin signing algorithm + tighten clock skew.** `Program.cs:56-63` doesn't set `ValidAlgorithms` (JWKS already constrains to advertised asymmetric keys, so low risk) or `ClockSkew` (default 5 min vs 15-min token = ~20 min replay window). Add `ValidAlgorithms = ["RS256"]`, `ClockSkew = TimeSpan.FromSeconds(30)`.
